## The question

> Can a team deliver something another person can actually use?

The project is where the four stages of the course stop being separate topics.
You start from real data, write and supervise the code that turns it into
something useful, structure and test that code so the team can work on it
together, and deliver it in a form that runs outside the machine it was built on.

## What a project integrates

| Stage | In the project |
| --- | --- |
| **Code literacy** | Code the whole team can read, explain and change |
| **Data** | A real source — files, a database, an API — with its meaning checked |
| **Engineering** | Structure, modules, documentation, tests, Git collaboration |
| **Production** | A reproducible environment and a usable application or product |
| **AI throughout** | Assisted development you can account for and defend |

## What is assessed

The project is graded on the delivery *and* on the evidence behind it: whether
the team can explain the code and the data, validate the results, reproduce the
whole thing from a clean start, defend the choices it made, and account for the
AI assistance it used.

Individual understanding is assessed inside group work. Being on a team does not
transfer responsibility for a result you cannot explain.

## Choosing a subject

A good DCM project is **small, real and checkable**, not ambitious and vague. A
modest dashboard over a dataset you genuinely understand, that reruns correctly
next week on new data, beats an impressive-sounding pipeline nobody can restart.

Ask early: what would it take for someone outside the group to run this, and to
believe the number it prints?
